# 升级与迁移

## 所有权边界

| 路径 | 默认所有者 | 更新行为 |
| --- | --- | --- |
| `.agents/skills/knowledge-hub` | 框架 | 未被用户修改时更新 |
| `Rules/Core` | 框架 | 未被用户修改时更新 |
| `Templates/Core` | 框架 | 未被用户修改时更新 |
| `tools` | 框架 | 未被用户修改时更新 |
| `Rules/Local` | 用户 | 永不覆盖 |
| `Templates/Custom` | 用户 | 永不覆盖 |
| 编号知识目录、`.obsidian` | 用户 | 永不覆盖 |

## 更新步骤

1. 单独克隆或下载新版本框架。
2. 在个人知识库中运行：

   ```powershell
   powershell -ExecutionPolicy Bypass -File .\tools\update-framework.ps1 `
     -FrameworkSource <新版本框架目录>
   ```

3. 查看脚本输出中的 `updated`、`added` 和 `conflicts`。
4. 人工处理冲突；脚本不会覆盖已修改文件。
5. 运行 `tools/verify-repository.ps1`。
6. 审阅 Git diff 后再提交。

升级到 `0.4.x` 时，在更新脚本之后运行一次 `tools/setup.ps1`。脚本将 KnowledgeHub 父目录作为现有实例的 `WorkspaceRoot`，写入不进 Git 的 `.knowledge/local-config.json`；它不会移动现有实例、覆盖 Obsidian 设置或修改用户资料。新安装默认使用 `%USERPROFILE%\KnowledgeHub-Workspace\KnowledgeHub`。

`0.4.0` 的发布状态文件曾错误保留 `installed_version: 0.2.0`。升级到 `0.4.1` 时，更新工具会把与新版本完全相同的文件安全登记，其余文件列为冲突而不覆盖；人工核对并对齐这些框架文件后再次运行更新工具，状态才会推进到 `0.4.1`。不要直接改写状态文件绕过冲突。

早期扁平目录实例如果缺少 `framework.manifest.json`、`VERSION` 或 `tools/update-framework.ps1`，不能直接运行自动升级；应先建立 Git 恢复点，再将旧规则和模板迁入 `Rules/Local`、`Templates/Custom`，最后安装当前框架管理目录。不要把 Setup 的 Existing 模式当作旧结构迁移器。

## 回退

更新前先提交当前知识库，或者建立临时分支。更新工具不删除旧文件；如果需要恢复，可使用普通 Git 历史回退单个框架文件。

## 版本策略

- 补丁版本：规则措辞、脚本修复、兼容性修正。
- 次版本：新增模板、工作流或可选工具，保持数据目录兼容。
- 主版本：可能需要人工迁移的目录或元数据契约变化。

框架当前不会自动联网或自动更新，避免在用户不知情时改变知识库治理行为。

## 发布维护

发布新版本时先更新 `VERSION`，再运行：

```powershell
powershell -ExecutionPolicy Bypass -File .\tools\refresh-framework-state.ps1
powershell -ExecutionPolicy Bypass -File .\tools\verify-repository.ps1 -StrictFrameworkState
```

提交生成的 `.knowledge/framework-state.json` 后，创建与 `VERSION` 完全一致的 Git 标签和 GitHub Release。
